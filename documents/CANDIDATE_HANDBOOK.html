Lead Engineer — Founder’s Technical +1

A four-hour, evidence-first assessment. PostgreSQL, Node/TypeScript and React/Next are the primary gates.

This is a job simulation, not a trivia contest, a certified IQ test, or free production work. You will reconcile conflicting business evidence, repair a deliberately imperfect local application, review another developer’s work, reason about AI automation, and learn a small unfamiliar module.

Start here: Candidate handbook · Hosted assessment desk · Downloadable documents · Reasoning test

Everything in this repository is synthetic. The fictional company is Northstar. No real customer data, company databases, advertising accounts, payment providers, messages, LLM credentials, or production systems are required or permitted. The application deliberately contains assessment defects. Do not deploy the API or database publicly. GitHub Pages hosts instructions and the reasoning form, not the backend.

What to do, in order

  1. Read 00 — Start here. Confirm the scope, rules, scoring, prerequisites, and submission route.
  2. Clone the starter and get the local environment working before the clock starts.
  3. Complete 01 — Reasoning, 40 minutes, no AI. Export your answers privately; do not commit them.
  4. Start the 200-minute practical with npm run session -- start.
  5. Read 02 — Business mission and 03 — PostgreSQL/database challenge. Prioritise a narrow, correct end-to-end repair over a broad rewrite.
  6. Complete the bounded AI/workflow, unfamiliar learning, and teamwork/code-review tasks. Learning is assessed separately from claimed expertise.
  7. At practical minute 110 run npm run session -- card. The change card is public; the timing rule is procedural, not a secret-lock claim.
  8. Finish using 07 — Submission. Deliver code, evidence, decisions and handover. Report incomplete work honestly.

Candidate handbook — start here

Your role in this exercise

You are acting as the hands-on engineering lead of Northstar, a fictional subscription-commerce business. The founder is unavailable during the exercise. Marketing wants to increase spend. Operations distrusts the numbers. A developer has suggested a quick patch. Your job is to establish what is true, choose a safe intervention, deliver working code and leave another engineer able to continue.

The assessment is designed for a senior full-stack engineer with Node/TypeScript, React/Next, PostgreSQL, technical leadership and AI/workflow experience. It tests primary skills deeply and secondary skills proportionately. You do not need to know Flutter already. You are not expected to build an entire business platform in four hours.

Before starting the clock

Ask the coordinator to confirm the paid-trial terms and time allowance before work starts; no amount or employment offer is implied by this repository. Agree any reasonable accessibility or scheduling accommodation up front. The assessment uses only fictional material and is not assigned production work.

  1. Clone assessment/start, create submission/attempt-01, record the starting commit.
  2. Install dependencies and start only the supplied local lab. Get the recovery desk and database working.
  3. With no dev server running, run npm test, npm run build, then npm run typecheck. Start npm run dev afterwards; do not build and run dev against the same generated directory concurrently. Record the output. If baseline setup fails, ask for environment help before starting. Do not spend your timed assessment fixing an organiser’s installation problem.
  4. Confirm the intended failing business tests with npm run test:challenge. Their failure is not an installation blocker.
  5. Read the table of contents, scope, standards and rules. Do not inspect timed reasoning questions or the timed change card early.
  6. Confirm a private return route for exported reasoning answers and any recording with the coordinator. No external email address or recipient is assumed by this pack.

Record Node, npm, OS, PostgreSQL and Flutter versions in your handover. Docker installation, package downloads and browser SDK setup are outside the timed work. If a machine/network fault occurs, notify the coordinator and log the interruption; an extension is a coordinator decision, not something to conceal.

Open the hosted reasoning form, or use the printable paper if necessary. Use an attempt ID, not your email/phone. Do not commit or publish reasoning answers.

This is a reasoning work sample, not a clinically validated intelligence test. Objective responses may be scored against a private answer key. Any integrity-related response is a human-review signal, not proof of your character.

Core acceptance expectations

  • Financial metrics are derived from documented business truth, not ad-platform attribution or the count of webhook rows.
  • Repeated/concurrent events do not duplicate a business effect. Use PostgreSQL for durable invariants; process-local memory alone is insufficient.
  • A failed, invalid or mismatched event cannot create a successful business outcome. Distinguish received, validated, recorded, completed and reconciled states.
  • Account identity applies at backend data access, not merely a frontend dropdown. Lab headers simulate authenticated context; they are not real authentication.
  • You can explain transaction boundaries, rollback behaviour and what happens after a worker restart.
  • The web UI has trustworthy account state, clear loading/error/empty states, and does not silently show stale values as current.
  • Your SQL/performance reasoning is backed by actual PostgreSQL output rather than a memorised “add an index” answer.
  • Your work is runnable by a teammate without personal IDE state, credentials or undocumented manual changes.

See the mission and database documents for exact contracts. The backend API contract and data dictionary define data semantics. Where a proposed change would break that contract, document the conflict and do not silently redefine truth.

Allowed and prohibited

Allowed during practical: official documentation, ordinary search, package documentation, AI coding assistants with disclosure, small open-source examples with attribution, your normal editor and terminal. Explain what the tools generated and how you checked it. Reusing provided infrastructure is preferred to needless rewrites.

Not allowed: assistance from another human doing the work, undisclosed help in the no-AI stage, employer code or confidential data, real platform credentials, live campaigns/messages/payments, pretending mocks are live proof, modifying test reports instead of behaviour, deleting tests to claim success, uploading personal information or reasoning answers publicly.

If you change a supplied test because you believe it contradicts the published contract, keep the original, add a new test and explain the discrepancy. Held-out evaluation will not trust your test changes automatically. A justified contract objection is welcome; silent weakening is not.

Published scoring and gates

Reasoning 15; PostgreSQL 30; Node/API 15; React/Next 15; AI/workflows 10; unfamiliar learning 5; teamwork/standards/handover 10. Total 100.

A suggested meeting-shortlist threshold is 75/100, with at least 18/30 PostgreSQL, 9/15 Node and 9/15 React, and independently verified core safety/correctness. These are assessment rules, not a job offer or an automatic employment decision. Strong overall points cannot erase an unresolved core cross-account leak or duplicate business effect. Work acknowledged as incomplete receives partial credit where independently supported. Do not hide a gap to chase a green score.

Qualitative work is reviewed by a human/technical evaluator using anchored rubrics, not auto-marked by matching prose to a string. The teamwork section tests a simulated interaction and handover; it cannot prove how you behave in a real team over time.

Evidence standard

Every important claim should point to a command, query, test, file/line, captured response or documented source. Keep code and explanation aligned. Save stdout/stderr and exit codes where useful. A screenshot of a green terminal is weaker than a reproducible command with the exact source revision. “It works locally” needs reproduction instructions. “Production-ready” requires more than this exercise can demonstrate.

Examples of useful statements:

  • “The replay test now passes against PostgreSQL; I have not load-tested across multiple API processes.”
  • “The query plan uses the proposed index on the supplied distribution; production selectivity is unknown.”
  • “I reviewed the Flutter change but could not execute it because the SDK was unavailable; here is the exact unverified boundary.”

FAQ

Do I need to meet the founder first? No. This pack is designed to be self-guided. The coordinator handles start/end and environment issues. Meaningful business questions should be written in your decisions document; make explicit, reversible assumptions where appropriate.

Do I have to finish everything? Core correctness and judgment matter most. The timebox is intentionally demanding. Prioritise, show real depth, and label unfinished work. Optional stretches are not hidden mandatory work.

Should I rewrite the app or switch databases? Usually no. Explain an exceptional reason before doing so. A rewrite that avoids demonstrating PostgreSQL, Node and React does not meet the primary-skill assessment.

Can I use AI? Not in reasoning. Yes in practical with disclosure, understanding and verification. No account/key is provided or required for a real LLM; the AI exercise is offline.

Can I ask questions? Yes. High-value clarification is good. Requiring the founder to make every technical choice is not. Do not let an unanswered noncritical preference block a safe, bounded decision.

Do the visible tests contain the whole answer? No. They are examples of the published contract. Independently generated cases may vary IDs, values, timing, accounts, retries and concurrency without changing the requirements.

Can I submit a ZIP instead of a public PR? Yes. Use the private handover route in the submission guide. Do not publish personal or cognitive-response data.

Can I change time settings or inspect future files? Technically public files and local clocks are inspectable. Do not misrepresent what you did. This pack does not claim secure exam lockdown.

What should I not build? No real advertising integrations, authentication platform, billing product, multi-agent system, Kubernetes cluster, fancy animations or full mobile app. Explain the necessary production changes as a short roadmap instead.

Practical mission — repair the business truth

Scenario

Northstar has two isolated business accounts, North and South. Each buys advertising, captures leads and sells orders. The business has separate campaign reports, order records and asynchronous payment event history. Some events repeat. Some are delivered late. Some records do not justify a financial conclusion.

The recovery desk currently runs, but its numbers and processing behaviour have not earned trust. Treat every stakeholder statement below as a claim to investigate, not authoritative truth.

Stakeholder notes — fictional

Marketing: “The attributed conversion number is rising. We should increase spend today. Our dashboard proves the campaigns are profitable.”

Operations: “Some people appear paid in one place and pending in another. We need a safe way to see the actual state and recover work. Please do not create duplicate orders or notifications.”

Backend developer: “We can check whether an event exists before inserting it, and mark the order complete immediately. The provider retries anyway.”

Frontend developer: “I can show whatever the summary endpoint returns. If requests fail, the previous numbers are probably better than an empty screen.”

Founder: “Give me the truth, the highest-value safe fix, and the decision you need from me. Do not bring me ten disconnected dashboards.”

Inputs and authority

Read fixtures/DATA_DICTIONARY.md, fixtures/seed.json, the synthetic CSVs, database/schema.sql, and server/API_CONTRACT.md. The API contract and data dictionary define the exact semantics. The marketing report is an attribution report, not a bank settlement statement. Payment event rows are observations, not automatically unique paid orders.

All financial values use integer paise and currency is explicit. Compare timestamps with timezone awareness. Keep account identity in every relevant join. State any rows you exclude and why. Do not guess profitability from revenue/ad spend alone: other costs and attribution certainty matter.

Part 1 — establish the truth

Write submission/DECISIONS.md, no more than two pages excluding evidence:

  1. What do the records actually establish? Give paid-order count, gross/net revenue as defined in the data dictionary, spend and revenue/spend ratio by account/campaign where justified.
  2. Which claims are unsupported? Distinguish bad measurement, broken processing, missing data and genuine business performance.
  3. What is the highest-risk/highest-value technical fix? What is second? What should not be built today?
  4. What decision, if any, genuinely needs a business owner? Give a recommendation and alternatives, not an unbounded list of questions.
  5. Name the source and query for each number. Do not hand-type unexplained totals into the UI.

Keep your query in submission/reconciliation.sql. Run it against the real lab database and preserve output.

Part 2 — PostgreSQL + Node core repair

The supplied service is intentionally incomplete. Repair the published business behaviour without weakening the contract. Preserve the API shape unless you document and implement a compatible migration.

Mandatory behaviour

  • Valid successful payments create the intended business effect once, including concurrent repeats and different transport event IDs referring to the same payment.
  • Invalid amounts, unsupported currencies, unknown orders and account mismatches do not create successful fulfilment/outbox effects.
  • Financial state changes, their durable event record and queued work have a defensible transaction boundary. A failure must not leave a partially completed business operation masquerading as success.
  • Account-scoped APIs cannot return or mutate another account’s order. Testing only the list endpoint is insufficient.
  • A late failure must not silently erase an authoritative success. Use the explicitly published provider/state rules; do not invent a reversal/refund from a failed event.
  • Worker retries/restarts must not duplicate a confirmed simulator side effect. Explain received/accepted/completed/unknown states and what you can actually prove.
  • Money is handled as integer paise, not floating-point currency arithmetic. SQL is parameterised; untrusted text never becomes SQL structure.

Write tests before or alongside each repair and show at least one meaningful failing-to-passing regression. The visible acceptance suite is not the entire grading universe. Do not hardcode seed-specific IDs or amounts. In-memory deduplication alone is not durable and is not enough.

The supplied simulator makes no real network calls. Do not replace it with a live provider. Extend it only inside the isolated lab to make a failure reproducible.

Part 3 — React/Next primary-skill task

Make the existing recovery desk a trustworthy view of the selected account.

  1. Rapid account switching must not let an old asynchronous response overwrite the new account’s data.
  2. Loading, errors, empty results and stale data must be visually distinguishable. A previous account’s values must not be represented as current.
  3. Recovery actions should show pending/result states and avoid accidental double-submission. Server-side invariants remain mandatory; button disabling alone is not idempotency.
  4. The display must use the API’s integer-paise contract consistently and avoid invalid/misleading ratios.
  5. Preserve accessible labels, keyboard operation, usable mobile width and a clear recovery flow.
  6. Add at least one browser or component-level regression that would fail on the original behaviour. Explain client/server responsibilities and any relevant caching choice.

You are not being graded on a visual redesign. Do not spend the timebox rebranding the application. The existing UI is deliberately small so you can focus on async correctness and operational clarity.

Part 4 — architecture and standards

Add a compact diagram to the handover showing the actual event/data flow and trust boundaries. Text or Mermaid is acceptable. Mark durable state, transaction scope, simulated provider boundary, retry ownership and account identity.

Answer concisely:

  • What is enforced by PostgreSQL, by application code, by the frontend, and by the provider simulator?
  • What changes when two API processes and two workers run concurrently?
  • Which failure requires reconciliation rather than a blind retry?
  • How would you deploy a schema change without hiding corruption, losing data or breaking an older application instance? Include rollback limitations.
  • What would you monitor first, and what should never appear in logs?

Do not submit a catalogue of technologies. Explain why each component exists. A simple monolith with sound invariants is preferable to unjustified microservices.

Part 5 — business and marketing judgment

This is an analytical task, not permission to operate Meta. In the decisions document, explain whether you would change budget now, what measurement uncertainty remains, and the smallest experiment or reconciliation you would run next. Separate attribution metrics, actual receipts, unit economics and causal lift.

Use official Meta documentation if helpful, but do not create an ad account, import audience data, send conversion events or use a real token. A conceptual browser/server event deduplication plan should specify stable identity and consent boundaries without claiming that our synthetic API is the real Meta API.

Scope discipline

Mandatory code: one narrow, reliable PostgreSQL/Node flow plus the bounded React async/error-state repair. Mandatory evidence: SQL reconciliation, database plan reasoning, regression tests, secondary exercise responses, learning attempt and teammate-ready handover. Optional stretches: load testing beyond supplied cases, complete observability implementation, production-grade authentication design implementation, or a larger mobile feature. Optional work cannot compensate for a broken core invariant.

If time runs out, stop, preserve the exact state, and identify the remaining risk. Do not fabricate a clean run or quietly delete failures. Your ability to make a safe, honest delivery decision is part of the assessment.

PostgreSQL challenge — primary gate (30 points)

This section is intentionally deep. Use actual PostgreSQL and show results. An ORM model diagram or an in-memory test is not sufficient database proof. Work only against the isolated assessment database provided by Compose.

A. Reconcile before you mutate

Using the data dictionary and schema, derive account/campaign financial truth with SQL. Show why a naive join from orders to payment events can multiply money. Distinguish event identity from business payment identity. Handle repeated observations, status precedence, refunds, currency, time boundaries and account identity exactly as the published fixture contract defines them.

Deliver submission/reconciliation.sql and output. Include conservation checks: raw rows, unique business entities, valid/invalid or excluded records, and totals. Where a value cannot be inferred, report unknown rather than silently substituting zero. You may add CTEs, window functions or views, but justify the method and keep the original source rows auditable. The raw repeated-delivery feed is in the fixture JSON/CSV; the reset database contains canonical event identities, not every raw delivery. For raw-feed conservation, combine explicit file-source counts with SQL, or stage a source-preserving raw copy in your isolated schema. Do not expect canonical payment_events to contain repeated transport rows.

B. Durable invariants and concurrent requests

Repair the core flow so the database protects the business effect under concurrent event delivery. The existing app may have superficially plausible application checks; demonstrate why your design survives races.

Required evidence:

  • Replay the same event sequentially and concurrently.
  • Send distinct event IDs referring to the same business payment.
  • Verify the resulting order/event/fulfilment/outbox state directly, not only the HTTP status.
  • Exercise a failed transaction and show what did not get committed.
  • Exercise the same order ID through the wrong account context.
  • Explain duplicate-safe constraints, foreign-key relationships and any state transition assumptions.

A correct answer explains where uniqueness belongs and why, not merely “use a transaction.” If you add a unique constraint, address existing duplicates before deployment. If you acquire a lock, explain what row/key it protects, ordering, timeout/deadlock considerations and the effect of multiple Node processes. Do not catch all integrity errors and call them success; distinguish a genuine replay from an invalid request.

C. Query-plan lab

The supplied database/performance.sql creates a separate deterministic performance fixture; it does not need real company data. Run:

npm run db:performance

Inspect the script and schema first. Use EXPLAIN (ANALYZE, BUFFERS) on the target query before and after a narrowly justified index/query change. Put your experiment in submission/performance.sql and the plans in submission/DATABASE.md or a linked evidence file.

Explain:

  1. Estimated versus actual rows, filter selectivity, scans, sorting and buffer work.
  2. Why the chosen column order suits this predicate/order/limit pattern.
  3. Which other workloads would pay for the index through writes/storage.
  4. Whether a sequential scan can be the correct choice on a small/low-selectivity table.
  5. How your conclusion depends on the supplied data distribution and cache state.

Do not claim a universal speedup from one wall-clock reading. There is no arbitrary millisecond pass threshold; plan reasoning and reproducible evidence matter. A proposal without a measured plan gets only partial credit.

D. Migration and recovery note

Write a short deploy plan, not a production deployment:

  • Preflight queries for duplicates/orphans/invalid values.
  • How to add/backfill/validate the chosen constraint or index.
  • Locking and availability risks, compatibility with old/new app versions.
  • What rollback can and cannot reverse after new valid data has been written.
  • How you would detect partial progress and resume safely.

No schema reset should be described as a production migration. npm run db:reset is a destructive lab-only convenience. Save your work/evidence before resetting. Never point it at another database.

High-load worker admission/pool redesign is optional, not a hidden core requirement. Preserve the provider's separate commit boundary when reasoning about recovery.

Standards you should demonstrate naturally

Parameterised SQL; integer money; explicit timezones; source-preserving reconciliation; appropriate constraints; connection cleanup; transaction ownership on one connection; bounded queries; deterministic tests with independent variants; honest benchmark interpretation; least-privilege production design. Explain what remains only a simplified lab convention, especially fake account headers and lab-only credentials.

04 — Learn a small unfamiliar Flutter boundary

20 minutes · 5 points · practical section · setup outside the timer. Flutter expertise is not assumed and this is not a mobile-platform build. We assess how you learn, reason and verify a bounded change—not prior Flutter vocabulary. Prioritize the core SQL/API/React work first. AI/docs are allowed with disclosure.

Goal

In mobile/, fix the invoice screen so only the latest requested load may change visible data, loading state or error state. A slow old request must not replace a newer result. Keep the API client injectable and existing user actions usable.

The tiny web-target Flutter app has two synthetic tenants, an asset-only fake API, integer-paise money, loading/empty/error/retry UI and smoke tests. There is no login, server, network API, mobile signing, store publishing or real tenant data. Fixing the UI race is not a substitute for server-side tenant authorization in a real product.

Setup (do this before timing)

Validated toolchain: Flutter 3.38.5 / Dart 3.10.4. The pubspec permits Dart 3.10–3.x; a different SDK is not promised identical dependency resolution. Use a prepared SDK or official Flutter installation. Do not burn the learning slot installing Android Studio, Xcode or emulators.

From the repository root:

cd mobile
# Optional: keep downloaded packages inside this ignored directory.
export PUB_CACHE="$PWD/.pub-cache"
flutter --suppress-analytics --no-version-check pub get
flutter --suppress-analytics --no-version-check analyze
flutter --suppress-analytics --no-version-check test

Open the loopback URL printed by Flutter. --suppress-analytics affects the command, not global Flutter settings. Do not run flutter config or upgrade the shared SDK for this lab. Dependency/SDK setup may need Internet; application data and model exercises are offline.

For a compiled web run instead:

python3 -m http.server 4329 --bind 127.0.0.1 --directory build/web

The no-CDN build bundles renderer resources; Python serves the compiled app. Stop either server with Ctrl-C. If port 4329 is occupied, use a free loopback port. Do not expose it publicly.

Read only what you need (~4 minutes)

  • State.setState: synchronous state mutation, then rebuild; do not make its callback async.
  • State.mounted: lifecycle validity after an await.
  • Dart async/await: a Future completes later; completion order can differ from call order.
  • Widget testing: pump advances a widget test; the supplied controlled client completes exact requests without sleeps.

Map these ideas to something you already know in React/TypeScript. Then read lib/main.dart, lib/api_client.dart, and challenges/latest_request_test.dart.

Work (~12 minutes)

Authoritative business rules

  1. One order, not one event, is the revenue unit. paidOrders counts orders.status='paid' even if fully refunded. Gross revenue is those order amounts once; net subtracts settled refunds linked to those paid orders. Pending refunds do not reduce net. No live refund API is required; the seeded refund ledger is authoritative. Do not join raw event or refund rows in a way that multiplies orders/spend. Ad-platform conversions/revenue are diagnostic attribution estimates, never accounting truth.
  2. Summary covers the complete supplied snapshot, all dates, only one selected tenant. No date filter is required. Reporting calendar for the CSV diagnosis is Asia/Kolkata; timestamps have explicit offsets and normalize to instants. Compare business dates in the correct zone, not string prefixes. Refunds do not revert paid status.
  3. Event identity is (tenant,eventId). Exact semantic replay is 200 with no new event/audit/outbox/fulfilment. Equivalent timestamp offsets denote the same instant. A changed payload under that identity is 409 with no writes.
  4. Business payment identity is (tenant,paymentId) and is permanently bound to one order/amount. Another event ID for that payment may add one observation/audit, but must not duplicate fulfilment. Payment identity reuse for another order is 409 and atomic. Different tenants may use the same IDs independently.
  5. Status precedence is succeeded > failed > pending, not last arrival wins; order precedence is paid > failed > pending. A late failed event can be retained as evidence but cannot revoke success. A pending/failed payment can later succeed. A different payment on an already paid order may be recorded, but must not create a second fulfilment or revenue unit. Resolving genuine overpayments is out of scope.
  6. New event, payment projection, order state, outbox intent and payment audit are one PostgreSQL transaction. A database failure at any write rolls everything back. Concurrent repeats must have the same outcome as sequential repeats. Database-backed identity/constraints and transaction ownership matter; an in-memory Set is not sufficient.
  7. One newly paid order generates one durable fulfilment intent. Seeded paid orders are historical and already serviced outside the replay window; no backfill jobs should be created for them. Seed runtime outbox/audit/receipts/fulfilments start empty.
  8. Provider acceptance and worker completion are separate durable states. The supplied provider uses a persisted business key and supports lookup/idempotent acceptance; a worker failure after acceptance must reconcile that receipt on retry, not invent a new key or blindly create another effect. No provider HTTP call exists. afterProviderAccepted is a programmatic test-only callback, not an HTTP fault flag.
